## 1. Problem

Turning a long video (lecture, product demo, vlog, event recording) into a short, watchable promo takes a skilled editor 1–3 hours: watching the footage, finding the strongest moments, ordering them into a trailer arc, and rendering per-platform formats. Creators and small teams either skip promos entirely or ship a random first-30-seconds cut.

**Product:** upload a long video → the system finds the high-impact moments across visual, motion, and audio signals → assembles them into a trailer-style promo (hook → build → climax → outro) → renders in platform aspect ratios.

## 2. Users

| User | Need | Priority |
|---|---|---|
| Solo creator / YouTuber | Turn a 20-min video into a 30 s Short/Reel teaser without editing skills | Primary |
| Small marketing team | Batch-standardize promos across a video library | Secondary |
| Student / hiring panel (portfolio context) | See a working, measurable ML + media systems capstone | Primary for this repo |

## 3. Current state (honest)

The deployed Django app accepts an upload and **byte-copies it to the output path** — an explicit mock in `promoapp/views.py` (current gap). The ML pipeline exists only as a standalone, non-runnable script `promoapp/promo4.1.py` (current gap — see [ARCHITECTURE.md §2](ARCHITECTURE.md)). An offline evaluation harness (`promo4.1.evaluate.py` + `labels.csv`) exists and defines the metrics below. Everything else in this PRD is **(planned)** unless stated otherwise.

## 4. User stories

- **US-1 (MVP):** As a creator, I upload an MP4 and get back a genuinely edited ≤30 s promo built from detected scenes, not a copy of my file.
- **US-2 (MVP):** As a user, I see job status (queued / processing / done / failed) instead of a hanging request.
- **US-3 (Capstone Demo):** As a creator, the promo follows a trailer arc — a strong hook first, rising energy, a climax, a clean ending — with no near-duplicate shots.
- **US-4 (Capstone Demo):** As a creator, I pick an aspect preset (16:9, 9:16, 1:1) and target duration before generating.
- **US-5 (Capstone Demo):** As a reviewer, I can see *why* each segment was chosen (per-signal scores surfaced in the UI/logs).
- **US-6 (Advanced AI):** As a creator, spoken hook lines are detected via transcript and can be burned in as captions.
- **US-7 (Production-Future):** As a team, we authenticate, keep job history, and store outputs durably.

## 5. Functional requirements

### MVP (Phase 1 in [ROADMAP.md](ROADMAP.md)) — (planned)
- **F-1** Upload MP4/MOV up to 500 MB / 30 min via existing upload page; validate extension, size, and that ffprobe can read the file. Reject with a clear error otherwise.
- **F-2** Real pipeline invocation: scene detection (PySceneDetect) → audio-energy + baseline visual scoring → top-segment selection → MoviePy render to a single 16:9 promo ≤30 s. (Repaired and refactored from `promo4.1.py` into `promoapp/pipeline/` — see [VIDEO_PIPELINE.md](VIDEO_PIPELINE.md).)
- **F-3** `PromoJob` DB record with status + progress; result page polls until done ([DATABASE_SCHEMA.md](DATABASE_SCHEMA.md)).
- **F-4** Playable result in browser + download link.
- **F-5** Failures recorded on the job with a user-readable message; no silent 500s.

### Capstone Demo (Phase 2) — the polished, show-off version — (planned)
- **F-6** Hybrid multi-signal scoring: CLIP zero-shot semantics + optical-flow motion + audio energy + frame-quality gates, fused per scene ([VIDEO_PIPELINE.md §4–5](VIDEO_PIPELINE.md)).
- **F-7** Narrative assembly: hook → build → climax → outro ordering with a scene-diversity constraint.
- **F-8** Aspect presets 16:9 / 9:16 / 1:1 with content-aware crop; target duration 15/30/60 s.
- **F-9** Live progress UI per pipeline stage (detecting scenes… scoring… rendering…).
- **F-10** Explainability panel: per-segment score breakdown by signal.
- **F-11** Evaluation report generated by the existing harness methodology (precision@K, AUPRC vs `labels.csv`), comparing hybrid scoring against single-signal baselines.
- **F-12** Title/outro text overlay (project name or user-supplied CTA).

### Advanced AI (Phase 3) — (planned)
- **F-13** faster-whisper transcription; transcript hook-phrase scoring joins the fusion.
- **F-14** Burned-in captions on the promo.
- **F-15** Optional LLM pass to pick the single best hook line from the transcript.
- **F-16** Fine-tune a small scoring head on `labels.csv` ground truth; ship only if it beats the zero-shot hybrid on held-out eval.

### Production-Future (Phase 4) — (planned)
- **F-17** Auth + per-user job history; Celery/Redis workers; Postgres; object storage; Docker + CI. See [ARCHITECTURE.md §6](ARCHITECTURE.md).

## 6. UX flow (Capstone Demo target)

1. **Upload page** (exists as shell today): file picker + aspect preset + target duration.
2. **Progress page** (planned): stage-by-stage progress bar, cancels on failure with reason.
3. **Result page** (exists as shell today): video player, download, per-segment explainability panel (planned), "generate another format" shortcut (planned).

## 7. Non-goals

- No general-purpose video editor (no timeline UI, no manual trimming).
- No multi-video compilation input; one source video per job.
- No music generation or licensed-music library.
- No real-time/live-stream processing.
- No mobile app; responsive web only.

## 8. Success metrics

| Metric | Definition | Target | Tier |
|---|---|---|---|
| Pipeline correctness | Output differs from input, ≤ target duration, ≥3 distinct source scenes | 100% of successful jobs | MVP |
| Selection quality | precision@5 of hybrid scorer vs `labels.csv` (methodology: `promo4.1.evaluate.py`) | Beats audio-only and CNN-only baselines with non-overlapping bootstrap CI | Capstone Demo |
| Ranking quality | AUPRC vs `labels.csv` | Reported per ablation; no fabricated target until first run | Capstone Demo |
| Processing speed | Wall-clock per input-minute on CPU | Measured and published; budget ≤2× input duration | Capstone Demo |
| Job reliability | Jobs ending in `done` or `failed`-with-message (never stuck) | 100% | MVP |

No engagement/watch-through numbers are claimed — there is no user traffic; those become KPIs only in Production-Future ([BRD.md §5](BRD.md)).

## 9. Constraints & assumptions

- CPU-only inference must work (Render/Railway free-tier class hardware); GPU is optional acceleration, never required.
- Model downloads (CLIP, whisper) cached at first run; cold start documented.
- `labels.csv` is the only ground truth; its size limits supervised training (hence zero-shot-first strategy, F-16 gated on eval).
- Python version must be reconciled: `runtime.txt` pins 3.10 but the pinned TF 2.20/numpy 2.2 stack needs 3.11+ (current gap, fixed in Phase 0).
